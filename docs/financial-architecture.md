## Release boundary and scope

`src/domains/finance/gate.ts` keeps both new financial execution and existing-obligation servicing false. Credentials cannot activate either gate. After separately authorized acceptance, new operations can be paused while servicing remains enabled. Do not turn servicing off while live obligations exist except under an approved incident plan.

This implementation covers Direct Payments, exact internal USDT, ordinary vendor purchases, protected delivery and internal seller settlement after the approved 24-hour hold. External cash-out is unavailable and disclosed. Funded escrow, refunds, affiliate features, additional providers/assets, analytics, full history pagination and a financial console are excluded. Existing policy primitives for those future features do not make them activation prerequisites for this scope.

## Accounting and provider boundary

Balances and journals use bigint micro-USDT, six decimals. USD is a reference price; no USD/USDT parity or redemption promise is assumed. Pay-in quantities use the selected network's precision and are never compared with USDT proceeds across different assets. Every journal has one positive quantity, distinct debit/credit accounts and a unique business reference. Database triggers enforce immutable records, deterministic account locks and sufficient funds. Member balances come from committed journals; pending means held seller proceeds, while unconfirmed deposits remain separate observations. Reserved balances show existing actual ledger entries, not invented reservations.

The existing server-only REST adapter calls NOWPayments Direct Payments within this interface. It issues one POST only after committing the external command's `outcome_unknown` claim. A timeout never resets that claim or causes another POST. All other recovery requests are reads. Provider secrets, raw responses and protected delivery payloads stay server-side. Creation, lookup, backing and callback evidence are retained encrypted with authenticated digest metadata.

`NOWPAYMENTS_APPROVED_ASSETS` admits exactly USDT/Ethereum (ERC-20) and one evidence-approved conversion asset/network. Missing approval exposes no payment options. The manifest records ticker, asset, network, precision, contract, memo requirement and an external verification reference. Its first entry must match the Ethereum USDT contract `0xdAC17F958D2ee523a2206206994597C13D831ec7`. It is approval metadata, not an activation switch. Runtime checks revalidate provider metadata, merchant selection, fixed-rate availability and the pair minimum before creation. Creation instructions must name the configured USDT outcome asset.

## Deposit path

1. An authenticated same-origin, rate-limited request binds a UUID to its original USD amount and selected asset. An unresolved earlier provider mutation blocks another creation. Preflight obtains the pair minimum and an indicative pay-in estimate before claiming the mutation.
2. The exact USD decimal is serialized as a JSON numeric lexeme without binary monetary arithmetic. `is_fixed_rate=true` and `is_fee_paid_by_user=false` request provider fee deduction from proceeds. Merchant conversion configuration determines the outcome asset; no unsupported request parameter pretends to configure custody.
3. Validated provider instructions persist exact pay-in amount, issued address, optional required memo, minimum, expiry and any estimated USDT receipt. The local QR contains the address only. The interface explicitly requires token/network/amount verification. Missing net/fee estimates are displayed as unavailable. A cross-asset fee estimate is unavailable rather than subtracting unlike units. Instructions stop being payable when expired, detected or under review.
4. Browser polling reads local progress. Explicit refresh performs an authoritative lookup. IPNs require documented HMAC canonicalization with constant-time comparison, safe numeric serialization and bounded input. Each signed receipt is retained durably and deduplicated; a processed duplicate does not reprocess the payment.
5. Lookup checks identity, original reference/address/memo, pay-in currency/amount, settlement currency, transfer hash and final actual net settlement. Progress regressions, partial/excess/late/wrong-asset/additional or ambiguous evidence enter sticky review. Missing creation-shaped recovery fields produce an identified review record, not an invented payable quote.
6. Credit requires authoritative `finished` evidence, positive final net USDT, the full expected pay-in and an unused transfer hash. Under shared system-account locks, available settlement funds must cover existing book backing plus this credit; pending provider funds are excluded. Evidence, balanced journal, actual credited amount, state and notice commit atomically. Provider errors or backing discrepancies prevent credit. Conflicting evidence after credit freezes financial activity and delivery without rewriting the journal.
7. Existing authenticated maintenance drains retained IPNs, recovers unidentified commands and polls known deposits. Recovery uses retained creation evidence, an identified payment lookup, or an exact reference match from a bounded payment-list window. Payment listing needs merchant read authentication. Missing, multiple or truncated results require operator recovery; they never prove nonpayment. Durable retry timestamps survive restarts and missed callbacks.

The configured provider's final-net and available-custody semantics must still be accepted for this merchant. Balance alone proves neither deposit attribution nor chain finality. No invented confirmation count or blockchain oracle is added.

## Checkout, delivery and seller proceeds

An authenticated checkout request binds buyer, selection and cart origin to a stable UUID. One current provider USD-to-USDT estimate is retained as rate evidence. The platform issues a fixed internal quote lasting five minutes, allocating the total exactly across selected purchased revisions. This quote is the platform's internal charge commitment, not a provider exchange-rate guarantee.

The customer sees delivery terms and the exact USDT total and explicitly confirms it. Purchase locks all buyer/seller members and financial accounts in canonical order, checks eligibility/freezes, quote expiry, current listing/revision, seller status, approved protected payload and sufficient available funds. A fresh available-custody comparison must cover existing liabilities. One database transaction commits every transfer from buyer available to seller pending, order, notice and purchased cart removal. A deferred database constraint rejects partial checkout commits. Repeating a committed checkout returns its existing orders without a second debit, including after quote expiry.

The committed order and purchased revision authorize delivery. Text is decrypted only at an owner-authorized download boundary. File entitlement names the purchased revision's exact approved private file. Buyer or seller financial freezes deny delivery. Manual orders use an immutable encrypted fulfillment submitted by the owning seller and presented on the protected order page; existing member messaging remains available for coordination. No new communication system is introduced.

The existing maintenance endpoint invokes seller settlement. Eligible paid/completed, unrefunded orders mature after 24 hours from payment. A stable settlement journal transfers seller pending to available exactly once, with a database-enforced hold and amount/account match. Available proceeds can fund internal purchases. They cannot be externally withdrawn in this release.
