# Migration preservation and recovery

Run all commands from the repository root. Never use schema push or edit applied SQL. `bun run db:migrate` uses the guarded runner; calling Drizzle directly bypasses it and is unsupported. The working tree contains a pre-existing edit to `0002_private_forum.sql`. Compare its SQL hash with each target's applied journal before proceeding. Do not rewrite an applied migration or its recorded hash; reconcile the difference through a reviewed preservation/forward-migration plan.

1. Disable application writes for the upgrade window. Inspect the intended database using `bun run db:inspect`. It reports only counts and a checksum, never row contents. Confirm the database identity in your operator console.
2. Take a full PostgreSQL backup (schema, records, sequences, triggers and migration journal) with your database provider or `pg_dump`. Back up all referenced private storage separately. Store both in restricted durable encrypted storage; record their checksums and retention. A JSON snapshot is not a substitute for these backups.
3. Before `0002` on a populated database, run `bun run db:preserve /restricted/path/snapshot.json`. The command writes a new mode-0600 file and refuses overwrite. It includes every public table: authentication records and other sensitive data must never be committed or printed. Preserve listings, original thread types, vouch listing references, avatars and synthetic-cleanup candidates. Review the cleanup predicate in `0002`; accounts with an authentication record are excluded.
4. Restore the full backup into an isolated database. With connection variables pointing exclusively to that restored database, run `bun run db:verify-restore /restricted/path/snapshot.json`. The receipt records a successful full public-row checksum comparison. Also verify restored sequences, triggers, journal, row relationships and storage retrieval. Keep the receipt beside the snapshot.
5. Repoint connection variables to the original database. Run `bun run db:migrate /restricted/path/snapshot.json`. The runner locks public tables, validates the applied journal prefix and SQL hashes, rejects changed snapshot contents, verifies the restore receipt, and applies pending SQL plus journal writes atomically. On failure the connection closes and the uncommitted transaction rolls back. Locks prevent writes between the final comparison and commit. Keep the maintenance window in effect until validation completes.
6. Validate canonical IDs, profiles/roles, real posts and replies, vouches, counters, usernames and private files before reopening writes. Preserve snapshots for the additive commerce legacy-import workflow. No catalog/category seeds are authorized. The runner does not bootstrap an administrator automatically.

For a genuinely empty database, `bun run db:migrate` needs no preservation manifest and applies the full journal in order. A database containing only initialized legacy tables/roles is conservatively treated as populated.

If `0002` already ran, it cannot recover dropped rows. Restore an older backup to an isolated database and capture the same snapshot there for the later mapped draft import. Without a backup, record the missing legacy data as unrecoverable. Never invent it or roll production backwards to recover it.

Before writes reopen, a failed upgrade may restore the verified backup. After writes resume, use forward correction; restoring old state requires capturing and reconciling all intervening writes. Do not drop new commerce or agreement records as rollback.

New schema ordering remains identity/preferences → sellers/taxonomy/listing revisions/favorites/cart → messages/delivery/outbox → order snapshots → deals/support/audit. Financial schemas now extend through forward migration `0017_marketplace_completion`, while money movement remains hard-disabled. Verified review submission remains unimplemented. October 1 local service fixtures and disposable real PostgreSQL checks applied the complete chain through `0017`; restored-production-data rehearsal and live application remain separately required. Extend fresh/legacy fixtures for every new migration.

## Legacy mapped import

After additive migrations and seller self-enrollment, run `bun run db:import-legacy /restricted/path/snapshot.json`. It preserves each original listing, related thread, posts and vouch references with a stable checksum. Records with a canonical enrolled seller and valid USD price become unpublished unavailable drafts without categories or invented protected payloads. Others remain `needs_review`. Rerunning resumes pending records after seller enrollment and does not duplicate mapped listings. A changed source checksum is an error requiring manual reconciliation. Inspect `/admin/legacy-imports`; no source secrets are rendered there. Unknown currencies/amounts are retained for review rather than converted speculatively.

Protected text backups require the matching DELIVERY_ENCRYPTION_KEY; keep it in an access-controlled secret manager with rotation/version planning. Losing the key loses access to encrypted payloads. Never rotate by overwriting the only copy. Owner-only paid-order text/file release code now exists behind the closed financial gate; it is not available in the pre-funding release.

## Marketplace completion — October 1, 2026

`0017_marketplace_completion.sql` is additive. It preserves historical same-asset settlement identity using nullable new settlement columns rather than updating immutable rows, introduces durable receipt recovery, checkout identity and encrypted manual fulfillment, and enforces committed purchase/24-hour hold/atomic checkout integrity. Existing `0000`–`0016` SQL was not rewritten by this implementation; the previously present `0002` discrepancy still requires comparison with applied hashes. No persistent migration ran.

The new `0017_snapshot.json` records the current TypeScript schema for subsequent generation; prior snapshot IDs/files are preserved. Its preceding metadata is the existing `0015` snapshot because custom `0016` had no snapshot. Snapshots do not replace migration SQL. Financial trigger functions, special constraints and operational indexes maintained directly in SQL must remain present during every forward migration. On an isolated restored copy, verify legacy requests, credited balances, journal/evidence digests, order identities and private deliveries before and after `0017`; inspect retained-IPN backfill and rollback by application pause without dropping financial data.

## USDT/Ethereum currency switch — October 1, 2026

`0018_usdt_ethereum.sql` is a forward migration for an empty financial subsystem. It locks and checks every financial table before changing defaults and the account currency constraint to USDT, with deposit network `eth`. It removes the historical USDC/Base contract default because each deposit request explicitly supplies its selected pay-in contract. It does not disable immutability, rewrite journals or edit `0000`–`0017`. Any existing financial record, including an empty old account, pending command, evidence or quote, causes rejection. Preserve such records and resolve the transition separately; never relabel assets.

The user authorized a database reset for this switch. Read-only inspection found no financial rows and all 17 applied migration hashes matched source; reset of unrelated community data is unnecessary. The pending `0017` and `0018` migrations were then rehearsed on a full isolated PostgreSQL restore and applied using the existing guarded runner. Every existing public-table record matched before/after; financial tables remained empty and USDT/`eth` defaults were confirmed. A full SQL backup, record snapshot and restore receipt are retained in restricted storage outside the repository (see VERIFICATION.md). No reset or provider payment occurred. Other databases still require their own hash comparison, backup and rehearsal.
